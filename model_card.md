## 1. Сведения о модели (Model Details)

| Поле | Описание |
|---|---|
| Название | Retail Demand Forecasting — XGBoost |
| Тип | Глобальная модель регрессии для прогнозирования временных рядов |
| Метод | XGBoost, ансамбль деревьев решений, обучаемых градиентным бустингом |
| Разработчик | Автор исследовательского проекта [SofiCholoian888](https://github.com/SofiCholoian888) |
| Задача | Прогноз количества единиц товара, продаваемых ежедневно, для пар «магазин — товар» |
| Горизонт | 28 календарных дней |
| Частота | Ежедневная |
| Объект прогноза | 500 временных рядов: 10 магазинов × 50 товаров |
| Целевая переменная | `sales` (в подготовленном формате — `y`) |
| Стадия | Экспериментальная модель, выбранная по результатам сравнительного backtesting; не заявлены API, оркестрация и автоматическая интеграция с закупками |

**Почему выбрана именно XGBoost.** В проекте сравниваются простые и статистические методы (Naive, SeasonalNaive, AutoARIMA, AutoETS, AutoTheta), модели ML (LightGBM, XGBoost, RandomForest) и DL (NBEATS, NHITS, TFT). В опубликованной единой схеме оценки XGBoost имеет наименьшую sMAPE — **12,975%**. Результат относится к данному набору данных и протоколу эксперимента, а не доказывает универсальное превосходство алгоритма.

## 2. Назначение и область применения (Intended Uses)

**Основное назначение.** Получить количественный прогноз продаж на следующие 28 дней для каждого сочетания магазина и товара. Такая оценка может помочь аналитикам изучать сезонность и ожидаемые колебания спроса, а при дальнейшей интеграции — обосновывать решения о пополнении запасов.

**Предполагаемые пользователи:** аналитики данных, исследователи моделей прогнозирования и, после интеграции с бизнес-процессом, специалисты по планированию ассортимента и запасов.

**Не предназначена для:**

- автономного размещения заказов поставщикам или управления запасами без дополнительных бизнес-правил и участия человека;
- прогнозирования цен, выручки, прибыли и индивидуального поведения покупателей;
- гарантирования уровня продаж или отсутствия дефицита;
- переноса без переобучения на новые магазины, другие категории товаров и существенно отличающиеся периоды;
- использования в качестве актуального прогноза для 2026 года без свежих данных и отдельной проверки качества.

## 3. Входные и выходные данные

### Исходные данные

Датасет: [Kaggle — Store Item Demand Forecasting Challenge](https://www.kaggle.com/competitions/demand-forecasting-kernels-only/data), файл `train.csv`.

| Поле | Тип / смысл |
|---|---|
| `date` | календарная дата наблюдения |
| `store` | идентификатор магазина |
| `item` | идентификатор товара |
| `sales` | фактическое количество проданных единиц |

В исходной выборке — **913 000 строк**, **500 рядов**, **1826 дней на ряд**, период **01.01.2013–31.12.2017**. Для анализа данные приводятся к формату `unique_id | ds | y | store | item`.

### Признаки модели

- Исторические значения продаж: лаги **1, 7, 14, 28** дней.
- Скользящие статистики (`rolling`) для представления локального уровня и динамики спроса.
- Календарные признаки: `dayofweek`, `month`.
- Идентификаторы `store`, `item` как статические признаки.
- Локальное масштабирование целевой переменной по каждому `unique_id`, чтобы одна глобальная модель могла обучаться на рядах разного масштаба.

**Правило доступности данных:** признаки для даты прогноза должны вычисляться только из информации, доступной к моменту соответствующего прогнозного среза (`cutoff`). Фактические `sales` из будущего окна недопустимы на входе. В данной реализации используется **прямая (direct) стратегия** многошагового прогнозирования. XGBoost применяется через обёртку `MLForecast` (библиотека Nixtla), которая для каждого шага горизонта `h` (от 1 до 28) формирует свой набор лаговых признаков (сдвинутых на `h`). Прогнозы на все 28 дней генерируются **независимо друг от друга** на основе исторических данных. Рекурсивная стратегия, при которой предсказанное значение подается обратно на вход модели, **не используется** (`recursive=False`), что исключает накопление ошибки по горизонту.


### Выход

Точечная оценка числа продаж для даты `ds` и пары `store`–`item` на горизонте 28 дней. Условная структура результирующей таблицы: `unique_id`, `ds`, `forecast` (это **описание контракта**, а не утверждение о буквальном имени столбца в ноутбуке). При оценке качества прогноз сопоставляется с реально наблюдённым `y`.

Прогноз количества товара может быть дробным: интерпретация и округление для закупок относятся к последующему бизнес-этапу и не входят в оценённую метрику модели. Калиброванные интервалы неопределённости для XGBoost не заявлены.

## 4. Значимые факторы и разрезы оценки (Factors)

Для качества прогноза потенциально важны:

- **Магазин и товар:** различаются уровни и закономерности спроса.
- **Сезонность:** в EDA обнаружены выраженные недельные паттерны.
- **Положение во времени:** ошибки могут меняться по месяцам, неделям и на разных прогнозных шагах.
- **Масштаб продаж:** ошибки на больших и малых рядах могут быть распределены неравномерно.
- **Нетипичные события:** наблюдения, отклоняющиеся от обычной динамики, могут ухудшать прогноз.

В опубликованном README представлены **агрегированные**, а не раздельные метрики по каждому магазину, товару, месяцу или шагу горизонта. 

## 5. Обучающие данные (Training Data)

Источник — хронологические продажи из одного набора Kaggle за 2013–2017 годы. Проект охватывает все 500 серий, а ML-модели обучаются **глобально**, используя общую информацию разных рядов. Перед моделированием проверяются регулярность дат, пропуски и дубликаты, исследуются тренд и сезонность.

Для обучения и оценки сохраняется временной порядок; случайное перемешивание по датам не используется.

## 6. Метрики качества (Metrics)

**Основная метрика — sMAPE (Symmetric Mean Absolute Percentage Error)**. Она показывает относительную ошибку между фактическими продажами и прогнозом; чем значение меньше, тем лучше. При нулевых/почти нулевых продажах показатель чувствителен к определению нулевого знаменателя, поэтому для точного воспроизведения требуется та же реализация метрики, что и в проекте.

Дополнительные метрики:

- **MAE** — средняя абсолютная ошибка, в единицах проданных товаров.
- **RMSE** — корень из средней квадратичной ошибки, в единицах проданных товаров; сильнее штрафует крупные промахи.

Метрика классификации (accuracy, F1, ROC-AUC) здесь не подходит: прогнозируется числовое значение продаж, а не класс.

## 7. Оценочные данные и методика (Evaluation Data)

Используется **rolling-origin backtesting**: для каждого прогнозного среза модель оценивается на следующих 28 днях, которые не должны входить в данные, доступные на дату среза.

| Параметр | Значение |
|---|---|
| Горизонт | 28 дней |
| Число окон | 3 |
| Сдвиг между окнами | 28 дней |
| Переобучение на каждом срезе (`refit`) | `False` |
| Число рядов | 500 |
| Число out-of-sample прогнозных точек на модель | 3 × 28 × 500 = **42 000** |

Данные для тестирования берутся из того же исторического датасета, но из более поздних временных окон. Это **не** независимый эксперимент на другом ритейлере и **не** проверка на современных данных.

## 8. Количественные результаты (Quantitative Analyses)

Результаты из [README проекта](https://github.com/SofiCholoian888/time_series_retail_forecasting):

| Модель | sMAPE, % ↓ | MAE ↓ | RMSE ↓ |
|---|---:|---:|---:|
| **XGBoost (выбранная)** | **12.975** | **6.168** | **8.101** |
| LightGBM | 13.042 | 6.200 | 8.141 |
| RandomForest | 13.083 | 6.194 | 8.112 |
| NHITS | 13.909 | 6.631 | 8.709 |
| NBEATS | 13.917 | 6.635 | 8.741 |
| AutoETS | 16.978 | 8.329 | 10.888 |
| SeasonalNaive | 21.067 | 10.499 | 13.982 |

XGBoost снижает sMAPE относительно AutoETS на **4,003 процентного пункта** (приблизительно **23,6%** относительно). По сравнению с SeasonalNaive улучшение составляет **8,092 процентного пункта**. Эти различия характеризуют указанный backtesting, но не являются отдельной статистической проверкой значимости.

## 9. Этические аспекты и риски (Ethical Considerations)

Датасет описывает продажи по идентификаторам магазина и товара; персональные данные клиентов в перечисленных полях отсутствуют. Основные риски имеют **экономический**, а не демографический характер:

- **Недопрогноз** способен привести к дефициту товара и потерянным продажам.
- **Перепрогноз** способен привести к избыточным закупкам и затратам на хранение.
- Неравномерность качества между товарами и магазинами может приводить к разным последствиям для подразделений.
- Автоматическое действие по одному точечному прогнозу без учёта поставок, остатков и неопределённости может создать операционные риски.

Поэтому модель рассматривается как вспомогательный источник для аналитика, а не как единственный механизм принятия решения.

## 10. Ограничения, рекомендации и дальнейшая работа (Caveats & Recommendations)

1. **Историчность и переносимость.** Данные заканчиваются в 2017 году. Перед практическим применением нужны актуальные продажи, проверка сдвига распределения и новая временная валидация.
2. **Нет бизнес-ограничений в самой модели.** Нельзя напрямую трактовать прогноз как оптимальный объём заказа: нужны текущие остатки, срок поставки, бюджет, минимальная партия и страховой запас.
3. **Неполнота неопределённости.** Опубликованы точечные прогнозы и ошибки; для решений о запасах полезны прогнозные интервалы/квантили, но они должны быть отдельно реализованы и проверены.
4. **Зависимость от временной схемы.** Используются 3 окна и `refit=False`; иное число срезов или переобучение способны изменить показатели.
5. **Проверка по сегментам.** До внедрения рекомендуется построить метрики по магазину, товару, периоду и горизонту прогноза, а также анализ смещений для рядов малого спроса.
6. **Контроль качества входных данных.** Следует отслеживать пропуски, даты, дубль наблюдений, неотрицательность продаж и отсутствие признаков из будущего.
7. **Эксплуатация пока не реализована.** Нужны сериализация и версионирование модели, повторяемый pipeline инференса, мониторинг качества и сценарий переобучения
