## 2. Intended Use — назначение

Модель помогает аналитику оценивать будущие продажи и сезонные изменения. После дополнительной интеграции прогноз может быть входом планирования запасов. Пользователи: аналитики, ML-инженеры, специалисты по ассортименту.

Не предназначена для автоматического заказа товара без бизнес-правил, прогноза цен/прибыли, гарантии отсутствия дефицита или применения к новым магазинам и категориям без проверки. Продажи — наблюдаемая величина, а не гарантированная оценка скрытого спроса: при дефиците товара спрос может превышать продажи.

Данные 2013–2017 годов не подтверждают качество на 2026 год. Инференс после обучения на исходном наборе выдаёт **01–28 января 2018 года**.

## 3. Вход, признаки, выход и стратегия

Входной CSV:

| Поле | Контракт |
|---|---|
| `date` | Календарная дата без часового пояса и времени суток |
| `store`, `item` | Положительные целочисленные идентификаторы |
| `sales` | Конечное неотрицательное число продаж |

Проверяются пропуски, дубли `(date,store,item)`, ежедневная сетка, одинаковые начало и конец рядов. Пропущенный день не считается нулевой продажей автоматически. Для полного набора флаг `--expected-series 500` проверяет число рядов; состав разрешённых store/item для реального бизнеса нужно задавать отдельным справочником.

После подготовки: `unique_id,ds,y,store,item`. `unique_id` — ключ ряда, а `store,item` используются как числовые статические признаки, без one-hot encoding.

Признаки:

- лаги `1,7,14,28`;
- средние `lag1 → window7`, `lag1 → window28`, `lag7 → window7`;
- календарь `dayofweek,month`;
- локальное стандартное масштабирование `y` по каждому ряду с обратным преобразованием прогноза.

**Стратегия рекурсивная.** `max_horizon=None`: одна модель прогнозирует следующий шаг, затем MLForecast использует предсказания в последующих лагах. Ошибка может накапливаться по горизонту. Параметр `refit=False` описывает повторное обучение между CV-окнами, а не выбор direct/recursive. Для direct в MLForecast нужен отдельный режим, например `max_horizon=28`; в этом проекте он не используется.

Фактические продажи внутри прогнозируемого окна недоступны. Между срезами уже наступившие факты допустимы. Масштабирование и лаги рассчитывает MLForecast; тесты проверяют отсутствие влияния будущих target на первое окно.

Выход CLI: `unique_id,ds,store,item,forecast`. Прогноз дробный, в единицах товара. Новая версия ограничивает **готовый** прогноз снизу нулём одинаково при оценке и инференсе; округления нет. Внутренние рекурсивные шаги используют исходные предсказания MLForecast до этого окончательного ограничения. Интервалы неопределённости не реализованы.

## 4. Factors — факторы качества

Качество зависит от магазина, товара, масштаба продаж, времени года, горизонта, промоакций, доступности товара и изменений ассортимента. В данных нет цен, остатков, сроков поставок и промо; модель не может непосредственно учитывать эти причины.

Новая оценка сохраняет разрезы по `unique_id`, `store`, `item`, шагу `h` и cutoff. Это позволяет увидеть ухудшение на отдельных сегментах; агрегированная метрика не является гарантией одинакового качества для всех товаров. Отдельная оценка сезонности требует большего числа временных окон.

## 5. Training Data — обучение

Источник: [Kaggle Store Item Demand Forecasting Challenge](https://www.kaggle.com/competitions/demand-forecasting-kernels-only/data), `train.csv`. По исходному исследованию: 913 000 строк, 500 рядов × 1826 дней, 01.01.2013–31.12.2017. При новом запуске фактический объём и hash фиксируются автоматически.

Одна модель обучается на всех рядах. Временные наблюдения не делятся случайным train/test split. Для backtest обучение первого окна заканчивается раньше первого прогнозируемого дня. Команда `train`, запускаемая после оценки, отдельно обучает финальную модель на всей предоставленной истории. Этот финальный артефакт нельзя оценивать на уже использованных им исторических данных как на независимом тесте.

## 6. Evaluation Data — схема оценки

| Параметр | Значение по умолчанию |
|---|---|
| Горизонт / шаг | 28 / 28 дней |
| Окна | 3 последовательных неперекрывающихся |
| `refit` | `False`: обучение в первом окне, обновление доступной истории в следующих |
| Cutoff исходного набора | 08.10.2017, 05.11.2017, 03.12.2017 |
| Проверочные периоды | 09.10–05.11, 06.11–03.12, 04.12–31.12.2017 |
| Размер на полном наборе | 500 × 3 × 28 = 42 000 прогнозных точек на модель |
| Baseline нового pipeline | SeasonalNaive с периодом 7, на той же точной сетке |

Результаты этого backtest использовались для сравнения алгоритмов в исследовании, поэтому не являются дополнительным нетронутым тестом после выбора модели. В новой версии автоматического подбора гиперпараметров нет. Для внедрения нужен отдельный более поздний holdout, не участвовавший в выборе, и актуальный внешний набор.

## 7. Metrics — метрики

Основная: `sMAPE_% = 100 × mean(2 × |y − ŷ| / (|y| + |ŷ|))`. При `y=ŷ=0` вклад равен нулю. Диапазон 0–200%; меньше лучше. `100 − sMAPE` не является accuracy. При очень малых продажах относительная ошибка может быть нестабильной.

Дополнительные: `MAE = mean(|y−ŷ|)` и `RMSE = sqrt(mean((y−ŷ)²))`, в единицах продаж. Метрики вычисляются по всем прогнозным точкам (micro averaging); на сбалансированной панели sMAPE также соответствует среднему по равновеликим рядам. Агрегированный RMSE не равен среднему RMSE отдельных рядов.

## 9. Ethical Considerations — последствия применения

В перечисленных полях нет персональных данных покупателей. Недопрогноз может привести к дефициту, перепрогноз — к излишним закупкам и списаниям. Ошибки по магазинам/товарам могут быть неравномерными. Модель помогает человеку, но не учитывает бюджет, остатки, срок поставки, минимальную партию или социальную значимость товара.

## 10. Caveats and Recommendations — ограничения

- Нужны свежие данные, оценка переноса и отдельный временной holdout.
- Три поздних окна не покрывают все сезоны и стрессовые ситуации.
- Холодный старт новых рядов не реализован; история должна быть непрерывной и выровненной.
- Входные числовые IDs не означают естественного порядка магазинов/товаров; это выбранное представление, которое стоит сравнить с категориальным.
- Точечный прогноз не измеряет риск. Перед управлением запасами нужны интервалы/квантили и бизнес-ограничения.
- Изменение seed/версий/оборудования может менять результат; lock и metadata повышают воспроизводимость, но не обещают побитовую идентичность на любых платформах.
- Сериализованные модели загружаются только из доверенного собственного запуска и в совместимом окружении.
- Планировщик, автоматический gate и production-активация пока описаны в [Model_retrain_BPMN.md](Model_retrain_BPMN.md), а не заявлены работающими.
